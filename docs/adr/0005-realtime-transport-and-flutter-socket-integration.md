# Realtime transport & Flutter-socket integration

**Status:** accepted

## Context

ADR 0001 scaffolded the Flutter client and reserved `lib/core/` as "where the socket-connection entry point will plug in," but didn't design it. Issue #6 (part of the build-ready spec map in #1) settles how the Flutter client owns and manages its Socket.IO connection: the client-side library and where it lives in the app architecture, the auth handshake after OTP login, reconnection/backoff behavior, and how ephemeral events (typing, presence) behave across a reconnect. It deliberately does not cover the message delivery/ack/dedupe contract (seq cursors, catch-up sync — issue #17) or local persistence (issues #7/#18); those are separate tickets this ADR's connection layer sits underneath.

Settling the auth handshake surfaced a gap in ADR 0003: that ADR guarantees revocation takes effect "immediately" for REST calls because auth middleware checks `Session.revokedAt` on every request, but a long-lived socket makes no such per-request check. This ADR closes that gap, and in doing so adds a "log out other devices" feature that didn't exist before.

## Decisions

- **Library: `socket_io_client`**, matching the backend's Socket.IO choice from `docs/features.md`/`CONTEXT.md` — not a real decision point, just confirmed.
- **Connection lifecycle: a single app-wide socket**, owned by a `keepAlive` Riverpod provider in `lib/core/` (alongside the existing `dio` provider), created when `AuthState` flips to authenticated and disposed on sign-out. Rejected scoping the socket to a chat screen's lifecycle — presence and cross-conversation notifications need to reach the conversation list even when no chat screen is open, and a per-screen socket would mean re-authenticating a new connection every time a chat opens.
- **App-lifecycle policy: explicit disconnect on background, explicit reconnect on foreground**, via a `WidgetsBindingObserver` — background is treated as a deliberate offline transition rather than left to the OS to notice. iOS in particular suspends the process without giving the socket a clean chance to detect its own death, so a deliberate disconnect avoids having to distinguish "OS killed it" from "we chose to close it."
- **`lib/core/` scope: connection plumbing only.** It exposes the raw connected `Socket` and a connection-status stream (connecting/connected/disconnected/reconnecting, watchable by any screen for a "reconnecting…" indicator). Each feature's own repository in its `data/` layer (per ADR 0001's feature-first split) takes the `Socket` as a dependency and wraps its own slice of events into typed streams. Rejected a monolithic `SocketService` in `lib/core/` that parses every event for every feature — that would grow `lib/core/` with every unrelated feature's socket events, contradicting its stated purpose as cross-feature infra, not feature logic.
- **Auth handshake: the access token is passed via the Socket.IO `auth` payload at handshake time**, not a query string (which lands in server access/proxy logs). The server rejects the handshake outright for an invalid/expired token, rather than accepting the connection and deciding afterward to boot it.
- **A validated socket is trusted past its handshake token's 15-minute TTL** (ADR 0003) — there is no periodic re-check of token expiry. The TTL was only ever a proxy for "catch a revoked session," and revocation is now pushed directly (below), so re-checking TTL on a timer would just churn a healthy connection's socket every 15 minutes for no security benefit.
- **Token freshness on (re)connect: proactive-first, reactive fallback.** Before any connect/reconnect attempt, the client checks the stored access token's expiry and refreshes it first if expired/near-expiry, reusing ADR 0003's single-flight Dio refresh logic. A server-side rejection (`connect_error`) is still handled reactively — refresh once, retry — as a fallback for that same attempt. This matters because Q5's background-disconnect policy makes "reconnecting after >15 minutes backgrounded" a routine case, not an edge case; a purely reactive design would guarantee a wasted round trip on that path every time.
- **Reconnection: `socket_io_client`'s built-in backoff, tuned rather than left at defaults** — short initial delay (~1s), capped max delay (~30s), randomization factor on (avoids thundering-herd reconnects after a server restart), infinite retries while the app is foregrounded.
- **Unrecoverable auth failure on reconnect** (refresh token expired past its 30-day window, or reuse-detected and revoked per ADR 0003) **stops the retry loop and routes to `/login`** via the same `AuthState`-clearing path Dio's refresh-failure interceptor already uses — one dead-session handling path, not a second one that diverges for sockets.
- **Session revocation propagates to already-open sockets by push, not by polling or waiting for a natural drop.** The server keeps a live-connection registry, `sessionId → Set<socketId>` (a session can briefly have more than one live socket during a reconnect handoff) plus a derived `userId → Set<sessionId>` index. Revoking a session force-disconnects every socket the registry has for it. This is what makes ADR 0003's "revocation takes effect immediately" guarantee actually hold for sockets, not just REST calls; the alternatives (a periodic per-socket re-check, or accepting that an already-open socket outlives its revocation until it naturally drops) either add polling overhead or quietly break that guarantee.
- **New endpoint: `POST /auth/sessions/logout-others`**, revoking every `Session` for the user except the one making the request — the "log out of all other devices" security action. The existing `POST /auth/logout` (ADR 0003) is unchanged and still revokes only the calling session. Rejected overloading `POST /auth/logout` with a `{scope: 'this' | 'all'}` flag: a flag that silently changes an existing route's blast radius is the kind of thing a client bug fat-fingers into logging out every device by accident. A "log out absolutely everything including this one" action, if ever needed, is just the client calling both existing endpoints back-to-back — not a third server endpoint.
- **Room subscription: server auto-joins the socket to every conversation room the user is a `Participant` in, at connect time** — the client does no explicit `joinConversation`/`leaveConversation`. Client-driven join/leave would race (a screen mounting before its join ack lands) and buys nothing here, since room membership is already fully known server-side via `Participant`.
- **Presence snapshot on (re)connect.** The same connect handler that auto-joins rooms also immediately pushes a presence snapshot for them, rather than leaving the client to piece together presence from incremental `userOnline`/`userOffline` events it may have missed while disconnected.
- **Presence display: never a confident "offline" for someone else while your own socket is disconnected** — show "last seen at `<time>`" instead, until the reconnect presence snapshot lands. "Offline" is a claim about another user's state that a disconnected client has no way to verify. Added **Presence** to `CONTEXT.md` to make this distinction (a user's actual, server-derived state vs. a client's possibly-stale belief about it) unambiguous.
- **Typing indicators are dropped unconditionally on reconnect**, relying on the ~6-second typing TTL (`docs/research/messenger-architectures.md`, P0-4) to self-heal, rather than trying to explicitly resume or verify in-flight typing state across the gap.

## Consequences

- The server needs a `sessionId ↔ socket` live-connection registry as first-class infrastructure — it now backs three things at once: message/presence routing, the auto-join-on-connect room model, and revocation push. This is a piece of state the earlier ADRs didn't anticipate needing.
- `POST /auth/logout` and `POST /auth/sessions/logout-others` both need to call into that registry to force-disconnect sockets, not just flip `Session.revokedAt` in Postgres — revocation is incomplete without the socket-side push.
- Any future feature needing "list my active devices/sessions" (a settings UI) has the server-side data it needs already (the `Session` table plus the live-connection registry for "currently active"), but that UI itself is out of scope here.
- Because a socket is trusted past its handshake token's TTL, the socket layer's security boundary is entirely the revocation push, not periodic reauth — a future change that weakens or drops the registry-based push would silently regress ADR 0003's "immediate revocation" guarantee with no other safety net catching it.
- Feature repositories (`ChatRepository`, `PresenceRepository`, etc.) each depend on the shared `Socket` from `lib/core/`, but own their own event parsing — consistent with, and extending, ADR 0001's "repository pattern in `data`, swappable/testable" rule to the socket source.
- The client now visibly disconnects and reconnects on every background/foreground cycle, not just on real network failures — the connection-status stream from `lib/core/` is what makes that visible in the UI (e.g. a "reconnecting…" indicator) instead of silently confusing users.
