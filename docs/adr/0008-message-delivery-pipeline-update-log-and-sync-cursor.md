# Message delivery pipeline: per-user Update log & Sync cursor

**Status:** accepted

## Context

Issue #17 (part of the Signal study map, #10) designs how messages and other durable changes reach Devices over Socket.IO: storage, ordering, dedupe, the connect/reconnect contract, the push hook from ADR 0006, and how delivered/seen receipts attach. The #10 map had picked Signal's **store-and-forward queue with ack-delete** (researched in #12). Socket.IO itself is at-most-once, and its connection state recovery isn't supported with the Postgres adapter, so correctness has to come from Postgres.

Signal's per-device queue exists because Signal's server is blind: the queue is the only server-side copy, deleted once delivered. Convoze is server-trusted (ADR 0007) and keeps every `Message` permanently (ADR 0004), so a per-recipient copy queue would be a second store of the same data that can drift from the first. This ADR keeps Signal's guarantee (at-least-once, ordered, ack-driven) but not its mechanism.

## Decisions

- **Per-user Update log + Device-held Sync cursor, not a copy queue.** Every durable change a User must converge on becomes an **Update** in that User's **Update log** (`CONTEXT.md`), numbered by a per-user `seq` that only goes up. Rejected: (a) a Signal-style `message_queue` with ack-delete (duplicates stored content); (c) a cursor straight over `Message` by UUIDv7 id (UUIDv7 order isn't commit order, so a slow transaction's message can be skipped, and it only covers new messages).
- **What is an Update:** new message, edit, delete, reaction add/remove, watermark moves, and membership changes (`conversation.joined` / `conversation.left` / `conversation.members`). Typing and Presence are never Updates (ADR 0005).
- **Shape: per-user fan-out, references not copies.** A table like `UserUpdate(userId, seq, kind, refs…, createdAt)`, unique `(userId, seq)`. A group message writes one row per member (sender included), and **groups are capped at 256 members** to bound fan-out. Rows carry references (`kind='message.new', messageId`); the server hydrates them to the *current* state when it drains, so a later edit drains as the latest state and deleted messages drain as tombstones. Rejected a per-conversation log + membership stream: no write amplification, but the cursor becomes a map and "which conversations changed?" needs its own stream.
- **`seq` assignment: per-user counter row, locked in the write transaction.** `UserSeq(userId, lastSeq)`; the writing transaction runs `SELECT … FOR UPDATE` on every affected user's row, **sorted by userId** to avoid deadlocks, bumps each counter, inserts the Update rows, and commits. Assignment is serialised per user, so for any user the visible order equals seq order and a pump can never skip a later-committing lower seq. Rejected a global `SEQUENCE` with Synapse-style "persisted up to" tracking: lock-free, but much harder to get right. Cost: a busy group serialises writes across its members, which is acceptable at this scale.
- **The Sync cursor is held by the Device, not the server.** The client's local DB (#18) stores the highest seq it has durably applied and sends it in the handshake (`auth: {token, since}`). There's no server-side cursor table: a server-held cursor can claim progress the client's DB never recorded (a failed write, a reinstall). The server uses acks only to move watermarks.
- **Retention and resync.** Update rows older than **30 days** are pruned. If `since` is missing, older than the user's oldest retained row, or ahead of their current `lastSeq`, the server emits `sync:reset {currentSeq}`. The client then rebuilds a snapshot over REST (conversation list plus the latest page per conversation, using the existing cursor pagination) and resumes from `currentSeq`. This is the same idea as Matrix's `limited` and Telegram's `differenceTooLong`.
- **One pump per socket, and it is the only thing that emits Updates.** On connect (after ADR 0005's room auto-join and presence snapshot), the pump reads `seq > lastSent` in batches of ≤100 and sends them with `emitWithAck('sync:batch', updates)` on a ~15s timeout. The client applies the batch to its DB in one transaction, dedupes by seq, then acks with the highest seq; the pump sends the next batch. When it catches up it emits `sync:caught-up` (Signal's `queue/empty`). A write never emits content live: after commit it just wakes the pumps of the affected users' connected sockets. Ordering therefore holds by construction, with no client-side gap buffering. On ack timeout the pump stops, and the next connect resumes from the client's `since`.
- **Send: socket `emitWithAck('message:send', {clientMsgId, …})`,** with the client's `ackTimeout`/`retries`. `clientMsgId` is a client-generated UUID, which is also the key of the optimistic row in the client's local DB. Unique `(senderId, clientMsgId)` makes retries safe: a retried send returns the original `{ok: true, messageId, createdAt}` instead of inserting twice. There's no REST send path, so there's only one set of validation.
- **Send guards and error contract.** Before inserting:
  - the sender must be a Participant;
  - text is capped at 4 KB;
  - media must reference an already-uploaded Cloudinary asset (ADR 0002);
  - an in-memory per-sender rate limit applies (~30 messages / 10s).

  Errors are returned as `{ok: false, code}` with `code ∈ NOT_PARTICIPANT | TOO_LARGE | RATE_LIMITED | INVALID`; only `RATE_LIMITED` is retryable (after a delay).
- **Blocking is silent.** In a direct chat with a blocker, the blocked sender's send acks `ok` and the message is stored and appears in the sender's own log, but no Update is written for the blocker. The sender sees one tick forever (WhatsApp's behaviour), and blocking isn't revealed. Blocks apply to direct chats and direct-conversation creation only; group messages are still delivered, and hiding them is a possible future client-side concern.
- **The sender's own log gets the message.** The sending Device finishes its optimistic row from the send ack, and later matches the drained Update on `clientMsgId` as a no-op. The sender's other Devices receive it normally.
- **Edits, deletes and reactions use the same path:** `message:edit`, `message:delete` and `reaction:toggle` via `emitWithAck`, each in one transaction that bumps seq and inserts Updates for every Participant (actor included). They are naturally idempotent: an edit sets a value, a delete is a soft `isDeleted` flag, and a reaction is covered by its unique constraint.
- **"Delivered" is reinstated as a Delivery watermark** (`CONTEXT.md`), amending ADR 0004. There's a per-Participant `lastDeliveredMessageId` that mirrors `lastReadMessageId` and moves forward only:
  - When a Device acks a batch, the delivery watermark moves to the highest message from others that the batch contained, per conversation.
  - `conversation:read {conversationId, messageId}` (with ack) moves the read watermark forward, and the delivery watermark with it: read implies delivered.
  - "Delivered to N" and "seen by N" are both counts over `Participant`.
- **Watermark moves are coalesced receipts Updates.** Kind `conversation.receipts`, referencing the conversation, with **at most one undrained row per (recipient user, conversation)**: a newer move deletes the older pending row and inserts a new one at a fresh seq. The row hydrates to the conversation's current watermarks. This avoids the ~65k rows per message that naive logging would cost in a 256-member group. The mover's own other Devices receive it too, which is how unread badges clear across Devices. Rejected logging receipts for direct chats only with live-only group receipts: that breaks the "everything durable converges" rule.
- **Membership changes mid-session.**
  - **Add:** one transaction inserts the Participant plus a `conversation.joined` Update for the new member and `conversation.members` for the existing ones. After commit, the registry joins the new member's live sockets to the room.
  - **Remove:** a `conversation.left` Update, and no Updates for that user from that transaction onward. Their earlier Updates still hydrate, since they were a member then. Their sockets leave the room.

  Socket.IO rooms now carry only typing and presence, never messages.
- **One socket per Session in steady state.** A new connection for a Session disconnects the older socket (close code 4409, "connected elsewhere", as Signal does), so each Device has exactly one pump. The registry keeps its `sessionId → Set<socketId>` shape; the seq dedupe makes a brief overlap harmless.
- **Push hooks in after commit, only for `message.new` from someone else** (plus a low-urgency push for being added to a group). Following ADR 0006's trigger, for each recipient Device with zero live sockets, `buildPush()` is called after commit and never inside the transaction. Edits, deletes, reactions and receipts never push. Muting (#10 chat list controls) will be a filter at this point.
- **Push on disconnect with unacked messages.** When a socket disconnects, any `message.new`-from-others Updates its pump had sent but not had acked are pushed, collapsed to one notification per conversation. This closes a gap in ADR 0006's binary trigger: a message that arrives while the app is foregrounded, just before the user backgrounds it (an explicit disconnect under ADR 0005), would otherwise never notify.
- **Single backend instance, stated as a constraint.** The registry, pump wakeups and rate limits are in-memory, with no Socket.IO adapter. Correctness lives in Postgres (the Update log, `UserSeq` and watermarks), so scaling out later means swapping the registry and the wakeup fan-out, not redesigning delivery.

## Consequences

- New tables: `UserUpdate` and `UserSeq`, and a new column `Participant.lastDeliveredMessageId`. Every durable write (send, edit, delete, reaction, read, membership change) goes through one shared "bump seq and insert Updates in the same transaction" helper; a write that skips it is invisible to other Devices until a resync.
- ADR 0004's "delivered is dropped" is reversed (a per-message status is still rejected; delivery is a watermark). ADR 0005's rooms no longer carry messages, and its per-Session socket set is at most one in steady state. ADR 0006's trigger gains the disconnect-with-unacked path.
- The client (#18) owns the Sync cursor. It must apply each batch transactionally before acking, dedupe by seq and by `clientMsgId`, and handle `sync:reset` by rebuilding a snapshot over REST.
- A 30-day retention window means a Device offline longer than that always resyncs from a snapshot. That is by design, not a failure mode.
- Group size is capped at 256 because of per-user fan-out; raising it notably would mean revisiting the log shape.
