# Media storage & flow

**Status:** accepted

## Context

`docs/features.md`'s Media Sharing section (feature 9) punted the storage decision: "use `multer`, store on disk/S3/Cloudinary... local disk storage + serve via static route is fine [for a 1-week build]; swap to S3 later." Issue #4 (part of the build-ready spec map in #1) revisits that punt, since this map is meant to produce a build-ready spec rather than throwaway scope. Chat media (images, files, short video) is potentially private — sent in 1:1 or group conversations — so the storage/delivery decisions also carry access-control weight, not just a "where do bytes live" question.

## Decisions

- **Storage backend: Cloudinary**, not local disk or raw S3/MinIO. Resolves the doc's punt directly rather than deferring it further, matching how the DB engine and auth mechanism were resolved outright in #1. Cloudinary's built-in image/video transforms (resize, format conversion, video-frame thumbnails) remove server-side processing code that S3 would require writing by hand — appropriate for a portfolio build.
- **Client-side picker/compression (Flutter): `image_picker` + `file_picker`** for selection, **`flutter_image_compress`** to downscale/compress images before upload. No client-side video compression for v1 — cross-platform video-compression packages are flaky and disproportionate effort here; raw video is capped by size/duration instead (see validation rules below).
- **Upload flow: direct-to-Cloudinary signed upload**, not proxy-through-Node. Node generates a short-lived signed upload signature via the Cloudinary SDK, scoped to an upload preset that enforces the validation rules below; the Flutter client uploads directly to Cloudinary using that signature, then reports the resulting `secure_url`/`public_id`/`resource_type`/`bytes`/`duration` back to Node in the "send message" API call. Node never receives media bytes, only metadata. Rejected proxying uploads through Node (client → Node → Cloudinary) because it doubles upload bandwidth and holds video uploads on the server twice as long, with no validation benefit once Cloudinary's preset is the enforcement point — this **supersedes** `docs/features.md`'s "use `multer`" note; `multer`/raw-file-handling is dropped from the Node backend entirely.
- **Validation rules (server-side, not trusting the client):** images — jpg/png/webp, ≤10MB. Files — pdf/doc(x)/zip/txt, an explicit allowlist rather than a denylist (a denylist misses executables renamed with a safe extension), ≤25MB. Video — mp4/mov, ≤60s duration, ≤50MB. Enforced via the Cloudinary upload preset referenced above, since Node never inspects raw bytes — the trust boundary is the preset the client cannot forge (it can't alter the preset without a valid signature), not app code sniffing content.
- **Message schema:** add `mediaPublicId`, `mediaResourceType` (`image`|`video`|`raw`), `mediaBytes`, `mediaDuration` (nullable, video only) to the `Message` model, alongside the existing `type: text|image|file|video` field from `docs/features.md`. No persisted thumbnail — derived on read via Cloudinary's URL-transformation syntax (e.g. `w_200,h_200,c_fill` for images, `so_0` for a video-frame thumbnail). No raw `mediaUrl` column — the servable URL must be signed at read time (see below), so storing a fixed URL would be wrong the moment it's written.
- **Delivery access control: Cloudinary `type: authenticated`** (private delivery), not public delivery. Chosen over public delivery + UUID `public_id` because a public, forever-guessable URL is a real privacy gap for potentially-private chat media — worth the added signing complexity, even though this build otherwise favors demonstrable-over-hardened tradeoffs elsewhere.
- **Signed-URL generation: never persisted.** Signed fresh, with a short TTL (~1 hour), at every serve point — the conversation-history REST endpoint (`GET /conversations/:id/messages`) and the Socket.IO emit handler for new messages both call the same signing helper at response time — and only after verifying the requesting user is a participant in that message's conversation, via the same membership check those endpoints already perform. Rejected signing once at send-time and persisting the result: that creates a stale-URL bug window once the TTL passes, and a TTL long enough to avoid that in practice stops functioning as real access control.

## Consequences

- The Node backend has no file-upload middleware (`multer`) and no code path that ever holds media bytes; its only Cloudinary-facing responsibilities are generating signed upload signatures (write path) and signed delivery URLs (read path), both metadata-only SDK calls.
- Every message-read path (REST history fetch, Socket.IO emit) must route media messages through the same signing-and-membership-check helper — a new media message type can't skip this and return a bare stored URL.
- Whether Cloudinary's upload-preset restrictions can hard-enforce the 60s video duration cap at upload time depends on the specific Cloudinary plan/tier in use — verify this during implementation; it isn't guaranteed by the preset alone on all tiers.
