# Push notification pipeline

**Status:** accepted — amended by [ADR 0008](0008-message-delivery-pipeline-update-log-and-sync-cursor.md) (push on disconnect with unacked messages); amended by [ADR 0009](0009-local-first-client-data-layer.md) (no push for muted conversations)

## Context

`docs/features.md`'s Push Notifications section (feature 12) sketched "FCM if you want mobile-ready" and "Web Push + service worker" for a generic web client; the latter doesn't apply now that the client is Flutter-only (ADR 0001). Issue #8 (part of the build-ready spec map in #1) designs the end-to-end pipeline: FCM/APNs setup, device token storage tied to the `Session`/device model (ADR 0003), the trigger condition `docs/features.md` names ("message sent to an offline/unfocused recipient"), and the payload contract between Node (`firebase-admin`) and the Flutter client. ADR 0004 deliberately deferred the push-token table to this ticket, naming `Session.deviceId` as the extension point. ADR 0005's explicit disconnect-on-background policy turns out to matter directly here: it collapses "offline" and "backgrounded" into the same signal.

## Decisions

- **Delivery transport: `firebase-admin` only, server-side — no separate native APNs integration.** The Flutter client uses `firebase_messaging` on both platforms; iOS tokens are still registered with APNs under the hood, but the server only ever talks to one API. Rejected a second integration (`node-apn` + `.p8` key) for iOS — real control (e.g. `mutable-content` + a Notification Service Extension) that this build doesn't need, on a solo/portfolio project where issue #1 explicitly favors clean, demonstrable architecture over production hardening.
- **New `DeviceToken` table, independent of `Session`.** `{userId, deviceId, platform, pushToken, updatedAt}`, unique on `(userId, deviceId)`. Considered adding a `pushToken` column directly to `Session` (which already has `platform` and is stable per device across its 30-day life via in-place refresh rotation, per ADR 0003) but rejected it: a push token's lifecycle isn't the session's — the FCM SDK can rotate a token in the background with no login involved, and a revoked-by-theft-detection `Session` shouldn't necessarily erase the row app-side reasoning about that device's token.
  - **No foreign key to `Session.id`.** Correlated only by the natural `(userId, deviceId)` key. A fresh login creates a new `Session` row while the device's push token is unchanged; an FK would orphan `DeviceToken` on every re-login for no reason. At send-time, "does this device have a live socket" is answered by looking up the current non-revoked `Session` for `(userId, deviceId)` and checking the ADR 0005 live-connection registry for its `sessionId` — a query-time join, not stored state.
  - **Registration: `POST /devices/token`**, auth-protected, upserting on `(userId, deviceId)`. Called after OTP verify / app start while authenticated, and again on `firebase_messaging`'s `onTokenRefresh`.
  - **Cleanup, two paths:** explicitly, `POST /auth/logout` and `POST /auth/sessions/logout-others` (ADR 0005) — which already force-disconnect sockets for the revoked session(s) — are extended to also delete the matching `DeviceToken` row(s); reactively, a row is deleted whenever an FCM send response reports that token unregistered (catches uninstalls, which never touch the logout path).
- **Trigger: binary, per-device — push iff that device's current `Session` has zero live sockets in the registry.** No separate "viewing this conversation" focus-tracking signal, and no new socket event to carry one. Cross-referencing ADR 0005: backgrounding is already an explicit socket disconnect, so "zero live sockets" already means "app not foregrounded" — a live socket means the app is foregrounded on *some* screen, and the in-app real-time message event plus an unread badge is what should handle "wrong conversation open," not an OS push. This matches Signal's actual rule (push iff not connected; online-only messages are dropped instead) and avoids inventing new realtime-protocol surface for this ticket.
- **Payload: a `notification` payload carrying sender name + message preview text, not content-free.** `docs/features.md`'s original P0-8-style content-free alternative (`data`-only, client fetches and renders on wake) was rejected for v1 because Convoze is server-trusted with E2EE a deliberate non-goal (ADR 0007), so content-free buys nothing today, and it requires an iOS Notification Service Extension this build doesn't otherwise need. Kept behind a single server-side `buildPush(message)` function, so switching to content-free later is a one-line change, not a rewrite. `conversationId`/`messageId` travel in the `data` portion regardless, for tap-to-deep-link.
- **Client display: always routed through `FirebaseMessaging.onMessage` while the process is alive; in-app affordance only, never a system banner, in that path.** This separates two concerns that could otherwise get conflated: the server's send-or-skip decision (above) versus the client's how-to-display decision. It also resolves a race the send-or-skip rule alone doesn't cover — app just foregrounded, socket still reconnecting (ADR 0005's proactive-refresh-then-connect isn't instant) — by downgrading that window to an in-app snackbar instead of ever risking a redundant system banner next to a live chat screen. Background/terminated: OS displays the notification; tapping it deep-links via `conversationId` from the `data` payload.

## Consequences

- The Node backend adds exactly one new table (`DeviceToken`) and one new endpoint (`POST /devices/token`); no schema change to `Session`.
- `POST /auth/logout` and `POST /auth/sessions/logout-others` (ADR 0005) each gain a `DeviceToken` delete alongside their existing socket-registry force-disconnect — revocation is incomplete without both from now on, the same shape ADR 0005 already established for the socket side.
- Any future message-send path (the actual persist-then-broadcast flow is issue #17's, not yet designed) must call `buildPush(message)` for each recipient after persisting, evaluated per-device against the live-connection registry — this ADR fixes the trigger/payload contract that path has to satisfy, not the path itself.
- Switching to content-free push later touches only `buildPush()` and the client's notification-rendering code — the Notification Service Extension work is deferred, not designed away.
